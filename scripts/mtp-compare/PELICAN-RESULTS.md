# Pelican SVG comparison, 2026-09-05

## Scope and controls

Question: `画一个鹈鹕骑自行车的svg`.

All speed cases used physical GPUs 2 and 3 sequentially: two RTX 4090 cards reporting 48 GiB each, on the same NUMA node. Other pre-existing workloads on other GPUs were not stopped. This is a shared machine, not an otherwise isolated host. vLLM's P2P test failed on this pair and its custom AllReduce was automatically disabled. Do not extrapolate these measurements to NVLink/P2P-capable hardware or the user's dual 3080 system.

Both engines received exactly the same 61 prompt token IDs generated by the supplied HF tokenizer/template, including its default xhigh system instruction and assistant `<think>` prefix. Temperature 1.0, top-p 0.95, top-k 20, min-p 0.0, presence/frequency penalty 0.0 and repetition penalty 1.0 were explicit. Raw completions bypassed engine-specific chat templating and reasoning-budget interventions. Actual output was checked: all measured 4096-token continuations remained in thinking, without `</think>`.

Each configuration had a 128-token request warmup followed by two 4096-token requests, seeds 1007843 and 1007844, concurrency one, prefix caching off and ignore-EOS on. Context capacity was 8192 and prefill batch cap 512. These are ordinary short-prompt, growing-context measurements, not 80K/262K tests or full SVG completion measurements. The short request warmup does not pre-capture every growing-KV shape in muse; subsequent captures are included in request latency.

- vLLM 0.28.0: supplied `/workspace/vllmvenv/.venv`, `/pubdata/llm_models/cyankiwi/Qwen3.8-27B-AWQ-INT4`, compressed-tensors INT4, BF16 KV, TP=2, OMP threads 1. Graph mode selected FULL_AND_PIECEWISE and successfully captured FULL decode graphs. `enforce_eager` disables compilation as well as graphs, so its comparison is not a graph-only ablation.
- muse build 10676 / 11aedacb2: existing `build-package-cuda13/bin/llama-server`, Q5_K_M GGUF, q8_0 target and draft KV, tensor split 1:1, internal AllReduce, mirrored output, backend sampling, 16 CPU threads. `GGML_CUDA_TP_GRAPHS=0` disables the outer TP capture, not backend-local CUDA graphs.
- MTP cases: three greedy draft tokens, no adaptive disablement, draft probability threshold zero. This intentionally differs from production adaptive MTP and threshold 0.2 to keep draft policy aligned with vLLM.

## Speed results

Values are means of the two client-observed streaming decode rates: `(completion_tokens - 1) / (last_text_event - first_text_event)`. Speculative chunks can carry more than one token, so this is an approximation. End-to-end rates include TTFT but exclude startup, warmup and metric-publication waits. Acceptance is total accepted draft tokens divided by total proposed draft tokens across both requests, not first-position acceptance.

| Configuration | Decode token/s | End-to-end token/s | Mean TTFT, ms | MTP acceptance |
|---|---:|---:|---:|---:|
| vLLM compiled + Graph, MTP3 | 94.32 | 94.04 | 136.7 | 43.42% |
| vLLM eager, MTP3 | 21.41 | 21.39 | 179.5 | 44.58% |
| vLLM compiled + Graph, no MTP | 76.19 | 76.03 | 126.7 | N/A |
| muse TP Graph, cache 256, MTP3 | 88.91 | 88.32 | 320.3 | 44.35% |
| muse TP Graph off, MTP3 | 85.03 | 84.37 | 385.2 | 44.35% |
| muse TP Graph, cache 256, no MTP | 62.75 | 62.43 | 344.3 | N/A |
| muse TP Graph requested, default cache 16, MTP3; fell back | 86.90 | 86.30 | 339.1 | 44.35% |
| muse TP Graph requested, default cache 16, no MTP; fell back | 62.56 | 62.33 | 257.8 | N/A |

On these configurations, vLLM Graph + MTP is 6.1% faster than muse with the larger TP graph cache. Without MTP, vLLM is 21.4% faster. vLLM's compiled/Graph mode is 4.41x its eager speed. Muse's larger-cache TP Graph MTP case is 4.6% faster than its TP-off case. These are small-sample descriptive comparisons, not statistical confidence claims. Cross-engine weight/KV formats and generated continuations differ, so these gaps cannot be attributed exclusively to graph implementation or kernels.

The two MTP acceptance measurements do not reproduce a substantially lower muse thinking acceptance rate on this prompt: vLLM 43.42%, muse 44.35%. Within muse, each seed produced identical output text and identical accepted/proposed counts in all three MTP graph configurations. This does not prove correctness for long contexts, other seeds, concurrent requests or rollback edge cases.

## Confirmed TP graph cache fallback

The default-cache MTP log contains:

```text
0.26.893.480 W TP CUDA graph cache reached 16 unique graphs; disabling TP capture and falling back to eager execution
0.49.427.346 W TP CUDA graph cache reached 16 unique graphs; disabling TP capture and falling back to eager execution
```

The no-MTP case also reached the limit. Source in `ggml/src/ggml-backend-meta.cpp` clears the captured graph cache and sets `capture_requested = false` when the unique-key limit is exceeded. This is not LRU eviction, and the same backend does not automatically resume TP capture on the next request. The two MTP warnings are consistent with separate backend contexts; the warnings do not identify their owner, so exact ownership is not inferred from them alone.

Supplementary cases changed only the cache cap to 256 and verbosity to 4. Logs confirm batch-4 target captures covering 161/162 subgraphs, plus MTP captures covering 5/6 subgraphs. Across warmup and two requests, MTP produced 78 successful capture log entries and the no-MTP case 34; neither logged fallback. There were no runtime crashes in these benchmark cases.

Larger cache capacity prevented the observed fallback but did not produce a large speedup. New graph captures continued as requests progressed. The cache key includes tensor shapes, addresses and operation parameters; a follow-up should trace which components create new keys before changing key semantics. Unsafe key reuse could replay stale pointers or operation parameters.

Increasing the cap to 256 is a diagnostic setting, not a demonstrated long-context solution. More graphs consume host/device resources, and a 262K request can encounter far more variants. The scoped next optimization is bounded cache behavior and safe shape/storage reuse, followed by CPU/GPU profiling of the residual latency. This run does not establish an AllReduce or full-attention bottleneck by profiling.

## Separate fixed-prefix first-MTP-step check

After all timing cases finished, reran `vllm_capture.py` with the same pelican question and explicit thinking sampling settings. This diagnostic uses eager mode, a 4096 context cap and a 256-token output cap; it is not included in the speed table. Replayed the captured prefixes on GPUs 2 and 3 using `muse_capture.cpp`, host hidden staging and q8_0 target/draft KV. The draft KV types are now explicitly assigned in the utility rather than relying on initialization behavior.

There were 114 capture records and 112 valid aligned comparison positions. The 256-token continuation remained in reasoning. For 111 fully observed three-draft rounds, vLLM accepted 142/333 draft tokens, or 42.64%; the final clipped round is excluded. This shorter diagnostic rate is separate from the 43.42% measured in the two long Graph speed requests.

| Metric, 112 matching prefixes | Result |
|---|---:|
| Target cross-engine top-1 agreement | 91.96% |
| First-MTP-step cross-engine top-1 agreement | 93.75% |
| Target mean JS divergence | 0.00548 |
| First-MTP-step mean JS divergence | 0.00659 |
| vLLM expected first-proposal acceptance | 67.29% |
| muse expected first-proposal acceptance | 67.83% |
| Draft argmax equals own target argmax, either engine | 78.57% |

Expected first-proposal acceptance is the target top-k/top-p probability assigned to its greedy draft token, not the observed acceptance of all three positions. This sample does not show degraded muse first-step proposal quality. It does not validate the second/third proposal, all rollback paths, or long-context behavior, and quantization/precision differences remain confounders.

Artifacts: `benches/pelican-logits-vllm/`, `benches/pelican-logits-muse/comparison.json` and the raw float32 tensors alongside it. Historical prime-proof artifacts and their results were not overwritten.
