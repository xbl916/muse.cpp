# 双 3080 继续工作交接（2026-09-05）

## 先读结论

1. 后续统一测试问题：**画一个鹈鹕骑自行车的svg**。保持思考模式，不能通过降低温度、提前结束思考或缩短生产上下文来冒充性能优化。
2. 双 4090 短问答测试没有复现 muse 的思考 MTP 接受率明显低于 vLLM：两者约 43%～44%。这不代表所有 MTP 问题已经解决。
3. **确实复现 TP Graph 缓存满后自动关闭捕获**：默认最多 16 张图，达到上限后清空缓存、设置 `capture_requested=false`。有无 MTP 都会发生。
4. 将缓存上限临时提高至 256 后，本次短测试不再回退，但 MTP 速度仅从关闭 TP Graph 的 85.0 提升至 88.9 token/s，约 4.6%。增大缓存不是长上下文的最终方案。
5. 当前包已经包含 3080 原生 `sm_86`、Release、`-O3`、`-use_fast_math`。仅改成只编译 `86`，主要缩小包体和缩短编译时间，不能期待明显提速。
6. 下一步优先做 **3080 上的 batch 1～4 量化矩阵乘微基准、算子融合、Graph 缓存与同步优化**。没有实测支持任何“专版重编后快数倍”的承诺。

## 本次提交是什么

这是从 `rollback-v14` 的基线 `11aedacb2` 继续工作的检查点，包含此前工作区积累的 TP Graph/internal AllReduce、paged sparse attention、MTP 概率验证与采样、reasoning/logging 等源码和测试修改，以及本次诊断脚本、报告和 `chat_templatev22.4.jinja`。

不要把这个提交理解为“上述所有问题已经修复并通过完整回归”。最近几轮主要是在现有构建上做数值对比和性能分析，没有实施新的 3080 内核优化，也没有修复 16 图缓存上限策略。本轮交接只补充文档、脚本可配置路径和基础检查。

模型、`build-*`、`dist`、原始 logits、Nsight trace/SQLite 和大型生成数据不随此次提交推送。报告中的 `benches/...` 是本台 4090 主机的原始结果位置，3080 主机拉取后不会自动获得这些文件；重要数字已写入随 Git 提交的报告，可用脚本重新生成原始结果。

## 已完成的测量

同一对物理 GPU 2、3（4090，报告 48 GiB/卡），顺序测试。vLLM 的 P2P 检查失败，自动禁用 custom AllReduce；muse 使用 internal AllReduce。其他已有 GPU 服务未停止。

统一 61 个输入 token，HF 模板默认注入 xhigh 指令并包含 `<think>`。并发 1、上下文容量 8192、关闭前缀缓存；128 token 预热后，两个种子各生成 4096 token，均仍在思考阶段。使用 ignore-EOS 固定输出长度，未测完整 SVG 最终作答质量。

采样参数：`temperature=1.0, top_p=0.95, top_k=20, min_p=0.0, presence_penalty=0.0, repetition_penalty=1.0`，frequency penalty 也为 0。MTP3 使用 greedy draft，关闭 adaptive 和低概率草稿截断。测速不导出 logits。

| 配置 | 平均 decode token/s | 总草稿接受率 |
|---|---:|---:|
| vLLM 编译 + Graph + MTP3 | 94.32 | 43.42% |
| vLLM 仅编译、Graph 关闭 + MTP3 | 32.29 | 45.50% |
| vLLM eager + MTP3 | 21.41 | 44.58% |
| muse TP Graph、缓存 256 + MTP3 | 88.91 | 44.35% |
| muse TP Graph 关闭 + MTP3 | 85.03 | 44.35% |
| vLLM 编译 + Graph、无 MTP | 76.19 | — |
| muse TP Graph、缓存 256、无 MTP | 62.75 | — |

补测 vLLM **不传采样参数**、使用正常 `--generation-config auto`：91.57 token/s、42.49% 接受率。日志确认模型自己的 `generation_config.json` 就是 `temperature=1.0/top_p=0.95/top_k=20`，因此不传参数不会变成明显不同的采样策略。种子与输出长度仍保留为测试控制项。

重要限制：vLLM 使用所提供的 compressed-tensors INT4 模型和 BF16 KV；muse 使用 Q5_K_M GGUF 和 target/draft q8 KV。不能把跨引擎速度差全部算作 Graph 差距。上述指标是客户端流式近似 decode 速度，小样本不构成统计置信结论。

## MTP 数值对比结论

鹈鹕问题的独立 256-token eager 诊断中，回放 112 个完全相同的前缀和 anchor：

- 第一 MTP 步跨引擎 top-1 一致率：93.75%。
- 第一草稿的预期接受率：vLLM 67.29%，muse 67.83%。
- 这不是三步总体接受率；该短 vLLM trace 的三步实际接受率是 42.64%。
- 当前样本没有显示 muse 第一步明显退化，但没有覆盖第二/第三步所有状态回滚路径、长上下文和并发槽位复用。
- muse 在两个种子下，TP Graph 开、关、默认缓存中途回退三种配置的输出文本和接受计数一致。不是通用正确性证明。

历史素数题结果保留在旧报告中，不要与鹈鹕结果混用，也不要拿带 logits 导出的运行速度测速。

## Profiling 给出的优先级

独立 Nsight node-level trace 中，muse 的矩阵乘相关 kernel 约占 **双卡累计 kernel 时间的 63%**，internal collective 约 17.6%，flash attention 约 4.0%，Gated DeltaNet 核心状态更新 kernel 约 1.0%。Gated DeltaNet 层内的投影矩阵乘已经计入矩阵乘类别，不能说整个 Gated DeltaNet 层只占 1%。

同一段 512-token muse 输出中，TP Graph 开关前后 GPU kernel 数都是 1,420,865；Graph launch 调用从 69,378 降到 3,150，说明提交确实合并了，底层算子工作量没有减少。TP Graph 关闭时仍有 backend-local CUDA Graph，并非 vLLM 的完全 eager 状态。

注意：node-level profiling 明显扰动执行，甚至让 TP-on 的 trace 比 TP-off 更慢；不要把 trace 内吞吐当正式速度。collective 时间包含等待，CUDA 同步等待与 GPU 工作重叠，不能直接相加成“可节省耗时”。

推荐顺序：

1. 在 3080 上提取真实 Q5/Q6 矩阵形状，分别测 batch 1、2、3、4 的 MMVQ/可选矩阵乘路径；检查 tile、warp、寄存器压力和访存。当前 dispatch 先判断 MMVQ，再判断 MMQ，盲开 `GGML_CUDA_FORCE_MMQ` 不保证能切换这个热点。
2. 对真实热点做 norm/activation quantization、兼容投影/激活等融合，减少中间读写和 kernel 数量，保持 q8 KV 并比对 logits。
3. 修复有界 Graph 缓存策略，追踪 shape/address/op-params 导致的新 key。不能简单删掉 key 中的地址或操作参数，否则可能回放旧指针和旧参数。
4. 检查仍存在的 stream 同步与 deferred gather。internal transport 的 gather 当前不进入外层 Graph，主模型通常捕获 161/162 个子图。先用低扰动 trace 确认关键等待，再选择改造方案。
5. CPU native/LTO 作为独立小实验，不要替代 GPU 热点分析。

## 3080 上如何接着做

**不要为了准备代码先停止已有服务或释放显卡。先准备好构建和替换命令，再切换自己的测试服务。不要停止无关 GPU 任务。**

先拉取本分支并检查工作区：

```bash
git status --short
git fetch origin
git switch rollback-v14
git pull --ff-only origin rollback-v14
```

如果本地有未提交改动或分支已经分叉，先处理冲突，不要 `reset --hard` 或强制覆盖。

建立单独的 3080 基线构建，不覆盖已有生产构建：

```bash
cmake -S . -B build-3080 -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_ARCHITECTURES=86 \
  -DGGML_CUDA=ON \
  -DGGML_CUDA_GRAPHS=ON \
  -DGGML_CUDA_FA_ALL_QUANTS=ON \
  -DGGML_NATIVE=OFF \
  -DGGML_LTO=OFF
cmake --build build-3080 --target llama-server -j 8
```

使用当地兼容的 CUDA Toolkit/驱动和现有 NCCL 依赖配置；上面不是自动安装依赖的命令。如果只测试 internal transport 且无 NCCL，可另加 `-DGGML_CUDA_NCCL=OFF`，但该构建不能用于 NCCL 对照。

如试 native/LTO，应另建目录、分别改变选项。`GGML_NATIVE=ON` 主要针对 CPU 后端，必须匹配 3080 主机 CPU，不要直接迁移另一台主机的 native 编译结果。

诊断脚本支持以下环境变量，不再要求沿用 4090 主机路径：

```bash
export MTP_COMPARE_GPUS=0,1
export MTP_COMPARE_MODEL=/你的路径/HF模型目录
export MTP_COMPARE_GGUF=/你的路径/模型.gguf
export MTP_COMPARE_MUSE_BIN="$PWD/build-3080/bin/llama-server"
export MTP_COMPARE_PORT=18991
```

用安装了 vLLM/transformers 的 Python 执行，子 vLLM 默认使用同一个 Python，也可指定 `MTP_COMPARE_PYTHON`。即便仅测 muse，脚本也需要 HF tokenizer 来生成统一输入，`MTP_COMPARE_MODEL` 仍要可读。确保所选两张卡和测试端口可用。

```bash
# 先复测短问答基线；每次使用新的结果目录。
python scripts/mtp-compare/pelican_bench.py \
  --out benches/3080-baseline --cases muse-tpoff-mtp

# 256 只是复现实验的缓存上限，不是满上下文生产推荐值。
PELICAN_GRAPH_CACHE=256 PELICAN_VERBOSE=4 \
python scripts/mtp-compare/pelican_bench.py \
  --out benches/3080-graph256 --cases muse-graph-mtp

python scripts/mtp-compare/pelican_summary.py benches/3080-baseline
python scripts/mtp-compare/pelican_summary.py benches/3080-graph256

# vLLM 只使用模型默认采样参数。
PELICAN_OMIT_SAMPLING=1 PELICAN_GENERATION_CONFIG=auto \
python scripts/mtp-compare/pelican_bench.py \
  --out benches/3080-vllm-default --cases vllm-graph-mtp
```

这些脚本的上下文容量仍固定为 8192，用于短基准；`PELICAN_COMPILE_NO_GRAPH=1` 是保留 vLLM 编译但关闭 Graph 的诊断覆盖，具体以保存的 command JSON 为准。

之后单独按原生产条件测真实 80K、160K、接近 262K 的输入/输出总长度，保留 `--max-model-len 262144`、q8 或更低 target/draft KV，并分别验证实际并发容量。不能只修改容量声明却用短输入，便宣称长上下文性能已经验证。生产 adaptive、草稿阈值、思考预算和稀疏窗口也要作为独立对照项，别同时改变。

建议验收：相同种子/模板/采样，至少两次预热后测量；保存 TTFT、decode、各位置接受计数、输出阶段、Graph 捕获/回退日志和显存峰值。CUDA 算子修改必须跑 `test-backend-ops` 数值对比；MTP 修改继续检查固定前缀第二/第三步及回滚。不要只拿平均 token/s 判定正确性。
